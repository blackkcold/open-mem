# 历史保留与会话冷归档设计

状态：用户已确认策略并授权实施；现已实现，证据见 PROGRESS.md。沿用主会话、现有工作树，不提交、不发布、不清理真实数据。

## 目标与已选策略
- UX 和可恢复性优先：恢复记录至少保留 90 天，且每类至少保留最近 20 次。
- 90 天不活跃的会话状态可冷归档；活跃记忆、当前队列和正在运行/排期的任务不清理。
- 清理必须先有只读预览，再由用户确认；后台维护不自动删除历史。
- 所有实现验证只使用合成目录。选择策略不是本次执行真实清理的授权。

## 方案
采用现有 JSON 文件存储，加确定性预览清单及快照校验。数据库迁移更重，且本轮不应迁移已有用户数据；无限保留不解决容量增长，故不采用。

## 实现边界
1. **保留单元**：维护 journal 与对应备份为同一组；curator 关联的维护记录按依赖一起保护。恢复记录、合并 journal、已归档 item 也受恢复引用保护。时间缺失、损坏、未知或进行中的记录保守保留并给出原因。
2. **预览**：健康页展示待删除文件/记录数、可释放字节、待冷归档会话数，以及保留原因。不展示私密原文。预览本身不写盘、不改状态。
3. **确认执行**：请求须携带预览指纹和用户确认。锁内重算并检查快照；数据变化即返回可解释的 409，请用户重新预览，不覆盖新数据。删除范围仅限 Store 数据目录内的已知历史路径，拒绝 symlink/越界文件。
4. **冷归档与续聊**：先写完整会话快照，再缩减 active state；读旧会话时可按 ID 找回冷归档状态，保留原扫描游标和固定上下文。冷归档本身不等于丢弃对话；归档是唯一游标/context 时，不按历史备份过期删除。无活动时间的旧状态不猜测过期；新活动补录时间。
5. **审计与失败**：记录策略、计数、确认时间，不记录被清理的私密文本。清理与审批/apply 共用持久化 redo WAL，初始化或下一次写入先重放，故障后不能把未完成提交当成成功。预览指纹包含完整待保留行集合，时间跨过 90 天而改变删除范围时也会失效。

## 验收
- 边界：89/90/91 天、至少 20 次、未知时间/损坏记录、恢复引用、进行中记录。
- 不动活跃记忆、队列、进行中会话；旧会话续聊能恢复扫描游标和 context。
- 预览零写入，缺确认拒绝，旧预览冲突拒绝；路径/symlink 攻击不触及边界外文件。
- 清理/冷归档中断后的重试不丢数据；健康页取消预览不产生写入。
- 完整 `npm run verify`，合成浏览器复核；不调用模型、不接触真实 store。

## 明确限制
90 天与最低 20 次是保护下限，不保证目录永远小于 20 MB。若保护窗口内数据已很大，UI 应说明无法安全释放的空间，而不是为满足配额删除恢复数据。用户需要预览并确认清理；无人值守自动删除不在本设计内。
